# Building PersonaKit: Day 5

This is Day 5 of writing about the build, not Day 5 of building PersonaKit.

And I reached the uncomfortable part.

Until now, it was easy to say the right things about AI memory:

It needs control.
It needs sources.
It needs permissions.
Approve / reject is not enough.
Memory should show up inside the work, not sit in a dashboard somewhere.

But now the product has to keep proving that this is not just a nice thesis.

I am building PersonaKit as a solo founder. That makes this part both easier and harder.

Easier, because there is no abstraction between the builder and the user.
Harder, because there is nowhere to hide.

The product has been moving toward this point for a while:

extracted memories,
reviewed claims,
permissions,
source-backed context,
and an MCP layer that brings memory into the tools where work actually happens.

PersonaKit should not be another place where people manage themselves like a database.
Not another dashboard of “all your memories.”
Not another layer that captures as much as possible and hopes the AI uses it correctly.

The direction is different:

Personal memory should enter the moment of work.

I am working with an assistant.
The assistant needs context.
PersonaKit returns relevant memory.
That memory comes with a source, scope, decision, and boundary.

Then the question is simple:

Did the answer get better?

Not whether the system looks smart.
Not whether the architecture is elegant.

Did the memory help when the assistant needed to understand me, my context, what I am in the middle of, and what it should not assume on its own?

Because when memory enters your real workflow, every mistake becomes visible.

If the memory is irrelevant, you feel it.
If it is too aggressive, you feel it.
If it brings something true but in the wrong moment, you feel it.
If it does not explain where it came from, you cannot trust it.

So the next step is simple:

I become the first real user of PersonaKit through MCP.

Not as a polished demo.
Not as “here are all my memories.”
But inside the actual work.

Claude Code / Codex / real assistants.
Real context.
Real questions.
Memory that should help now, not someday.

And that changes the question I am building around.

Not:
“How much can I capture about the user?”

But:
“Which memory is allowed to enter this working moment, why, and what can the user do about it?”

Because personal memory is not just storage.
It is an intervention in context.

So today is a small phase shift in how I talk about PersonaKit publicly:

Less explaining the memory thesis.
More showing the product standard.

The MCP path is getting close to the first real users.

Before opening it up, I want it to pass the test on my own work first:

real workflow,
real context,
real consequences,
and memory that earns its place in the answer.

If it works there, the next step is not “someday users.”
It is the first users, with the same standard.
